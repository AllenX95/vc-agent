# Use A Minimal VC Prompt And Task-Activated Capabilities

Accepted: every ordinary model call includes one concise, stable Minimal VC System Prompt and a small, scope-compatible common-read surface. The Host keeps a bootstrap capability broker visible so the model can discover or request additional capabilities when the initial hints are incomplete. Skills enter context only when invoked or otherwise explicitly activated.

This preserves a real VC-vertical identity while using Pi as a Minimal Default Harness rather than inheriting a broad coding-agent prompt and all available tool schemas. Scope and runtime policy determine which common reads are initially visible; deterministic intent signals are preload hints, not a correctness gate. A registered capability broker exposes a bounded catalog and revision-checked activation path for capabilities that are not initially visible.

The trade-off is an occasional extra tool round trip and dynamic tool-surface management instead of either loading every schema or relying on brittle complete intent classification before reasoning starts. Activation cannot expand authorization, silently load Project State, Memory, material bodies, or Skill instructions, persist as a standing Thread mode, or initiate Dream, Reflection, Thread Scope Elevation, or Sub-Agent delegation without their required explicit User intent.

The ordinary Project surface may include capability_request, material_recall, project_state_recall, web_search, and web_fetch; an Unscoped Thread omits Project Context and limits Material access to direct Thread attachments. Memory and Output remain policy-filtered, while protected cognitive and delegation workflows require explicit User initiation before their support capabilities may be exposed. Host management operations never enter the model tool surface.

The shipped default Minimal VC System Prompt is limited to six stable responsibilities: VC identity, independent judgment, Evidence Discipline, Memory's non-authoritative status, on-demand context discipline, and the User Intent Gate. Workflow stages, document templates, tool tutorials, Dream or Reflection procedures, Project facts, current Memory content, and Skill instructions belong to task-activated layers rather than the base prompt.

MVP does not impose a numeric token target or hard cap on this prompt. Minimality is a design discipline: every addition must justify why it is stable and necessary for nearly every ordinary VC conversation, while actual prompt, tool-schema, and total input usage remain observable through telemetry. Moving always-on text into a differently named default appendix does not satisfy this rule.

The User may directly edit the complete Minimal VC System Prompt. Every save creates a System Prompt Revision with diff and restore-default support; the app may warn about an empty prompt, removed VC identity, or unusually broad instructions but does not prevent the User from activating the revision. Host-enforced authorization, path boundaries, provider policy, and Memory-write confirmation remain effective regardless of prompt content.

Prompt edits follow Claude Code's `CLAUDE.md` lifecycle semantics rather than hot-reloading an active context. A Thread loads the active System Prompt Revision at a Prompt Load Boundary and keeps that revision through the current physical context. Editing or activating another revision affects the next new Thread, Thread Compaction/rebuild, or app-restart resume; it does not retroactively change the active context or invalidate its prompt cache immediately. MVP provides no same-Thread clear, reset, or fresh-start operation: the User creates a new Thread when a clean context is required, while automatic and User-invoked compaction remain available for continuing the current Thread. The product records a visible revision-change event when a logical Thread crosses a boundary and the loaded revision changes.

Investment Reflection and Dream are resumable multi-stage workflows rather than ordinary Thread contexts for prompt-reload purposes. Each run records a Workflow Prompt Snapshot when it starts, and every stage, selective rerun, and post-restart resume continues to use that revision. A later prompt activation does not make completed workflow results stale or mix revisions inside the run; it applies only to a newly launched Reflection or Dream run. This favors internally consistent and auditable learning over immediately applying prompt experiments to unfinished memory work.
