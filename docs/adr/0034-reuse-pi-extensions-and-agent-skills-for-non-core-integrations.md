# Reuse Pi Extensions And Agent Skills For Non-Core Integrations

Accepted: the first release does not build full native Office, MCP, Skill-package management, or multi-provider OCR subsystems. Office document creation and editing primarily reuse compatible document Skills; MCP connectivity reuses a selected Pi Extension; Skill discovery, validation, progressive disclosure, and package mechanics reuse Pi; and OCR uses one User-configured Skill, Extension, command, service, or API rather than an ordered Provider Chain.

ADR 0036 fixes the Personal Build's Office path to User-supplied Claude Code Office Skills, and ADR 0037 fixes the MCP path to a controlled, pinned `pi-mcp-adapter` integration.

Delivery is deliberately staged. Foundation, Dogfood Build, and Learning Build load only the app-bundled reviewed pinned Extension inventory and provide no arbitrary Extension acquisition or partial admission path. The full Extension Audit Workflow, User admission, Global Extension Enablement, atomic revision changeover, and rollback arrive in the Integration Build so package-governance work cannot delay validation of the core VC loop. Earlier stages may preserve the strict loader boundary and compatible storage contracts but must reject every non-bundled Extension.

VC Desktop retains the product boundaries that ecosystem packages cannot own: one isolated VC Agent Skills Directory, explicit Skill Import by complete-directory copy, Task-activated Capability exposure, Project and external-submission authorization, output provenance, edited-copy defaults, and confirmation before replacing Original Source Files or performing write-capable MCP actions. This reduces non-core implementation scope while accepting dependency compatibility checks, visible unavailable states, and no automatic fallback when a selected ecosystem capability fails.

Skill import and Extension admission are separate trust paths. Compatible Skills may be imported explicitly from a local directory or immutable Git/package source into the isolated Skills Directory. A new Pi Extension is first copied into a non-executing staging area and must undergo Extension Admission Review before the User may admit it to the same approved inventory as bundled, reviewed, pinned Extensions. Deterministic checks and any LLM-assisted source review produce an advisory report only; they cannot make the admission decision. Approval is an explicit User action and records the User decision, audit report revision, exact content hash, pinned source revision, dependency lock, executable entry points, declared permissions, compatibility result, and review evidence. A code, dependency, source, or permission change invalidates approval and requires a new review and User decision.

The review combines exhaustive deterministic identity and dependency checks with risk-directed LLM review. It inventories and integrity-checks the complete dependency closure, lifecycle scripts, native binaries, entry points, declared permissions, licenses, and known vulnerabilities. LLM review examines the Extension-owned source, lifecycle scripts, and privileged or otherwise high-risk direct dependencies; transitive dependencies are inventoried and scanned but are not represented as having received complete line-by-line model review. Missing immutable identity, complete artifact contents, or deterministic dependency resolution is an Extension Admission Blocker that the User cannot override. Findings about a fully reviewable artifact remain visible Extension Risk Findings that the User may accept explicitly.

Deterministic inspection is a Host-only Operation and may finish without Pi or a Model Profile. LLM review runs only as a User-launched Extension Audit Workflow with its own Physical Model Context, minimal versioned audit instructions, `Extension Audit` Task Model Assignment, and optional launch-time Profile override. It receives only the staged artifact and deterministic evidence, never Project files or state, ordinary Thread history, VC Skills, Project Memory, Long-term Memory, or investment prompts. Its trajectory and report are excluded from Dream and Memory eligibility. Missing Profile or Provider Failure preserves deterministic results and pauses the workflow without borrowing another task's Profile, switching Provider, or affecting ordinary Threads.

Only Approved Pi Extensions may be loaded by an Agent Worker, and approval does not enable an Extension automatically. Enabling is a separate explicit installation-wide User configuration action. Global Extension Enablement applies uniformly to every Project and Unscoped Agent Worker; the first release does not provide per-Project or per-Thread Extension profiles. This avoids hidden behavioral differences between Projects at the cost of granting every enabled Extension potential Worker-level visibility wherever the User runs the Agent. Once enabled, an Approved Pi Extension is Trusted Worker Code: it can use the Agent Worker's effective Node.js and OS process authority, including behavior that does not cross the Host Capability Gateway. Standard Access can mediate only the Extension actions that deliberately use Host-registered proxies; it cannot be represented as intercepting direct filesystem, network, subprocess, session, or in-process data access by Extension code.

Global Extension Enablement affects runtime loading, not model-context loading or Host authorization. Extension-provided tools and instructions remain subject to Task-activated Capability exposure, and Project paths, external submissions, durable product-state commits, and other Host-proxy operations retain their existing scope rules. Disabling is also installation-wide and prevents the Extension from entering subsequently created or rebuilt Workers.

Enablement, disablement, version replacement, and rollback each create a pending Global Extension Revision rather than hot-modifying individual Workers. By default, the current revision remains effective for all old and new work until every Agent Worker reaches an Extension Changeover Boundary with no Active Turn. The Host then atomically activates the pending revision and terminates all old-revision Workers; Lazy Agent Activation recreates them on later submitted work. This preserves one effective Extension set across Projects and avoids mid-Turn lifecycle mutation.

The User may explicitly apply a pending revision immediately after a warning that every Active Turn will be interrupted. The Host stops those Turns, terminates all Workers, activates the revision atomically, and never resumes or replays interrupted work automatically. A replaced artifact and its approval record remain available for explicit rollback while their bytes and approval identity still match; rollback is another pending Global Extension Revision and follows the same boundary. No update, rollback, enablement, or disablement occurs automatically.

Neither Standard Access nor Full Access permits an unreviewed Extension to execute or lets the Agent approve one; Full Access changes Host-mediated tool confirmation behavior rather than the Extension admission boundary or Worker-level trust. Review reduces risk but is not represented as a hostile-code sandbox or proof of safety. If the User will not grant Worker-level trust, the package must be rejected or redesigned as a Host-registered Capability or an isolated Skill job. The app may report available updates and sanitized failures, but it does not automatically install dependencies, update, approve, enable, retry, downgrade, switch packages, or choose a fallback capability.
