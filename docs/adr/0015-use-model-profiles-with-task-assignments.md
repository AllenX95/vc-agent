# Use Model Profiles With Task Assignments And Manual Override

Accepted: Provider and Model configuration is encapsulated in reusable Model Profiles, while each product task type has a separately configurable Task Model Assignment. The Prompt Composer exposes the Active Model Profile and permits a Thread Model Override that persists until changed or restored without mutating the task default; independent Dream and Investment Reflection workflows use their own task assignments and explicit launch-time overrides. This avoids hard-coded model routing and preserves user control across third-party Providers, at the cost of maintaining profile validation, assignment resolution, override scope, and visible provenance for the model actually used.

Before execution, the Host compares only the current task's indispensable model capabilities with lightweight Pi or Provider metadata. A known compatible Profile proceeds; a defined degradation remains visible; and an unsupported task stops with a specific incompatibility. Unknown metadata is not treated as a guarantee, runtime errors supersede cached claims, and neither capability failure nor Provider Failure may automatically select another Profile or Provider. The User changes the Profile and retries manually.

A same-Provider Profile change continues the current Thread. A cross-Provider change requires the User to choose either Cross-Provider Thread Continuation, which sends the new Provider the Thread's retained context and treats that selection as authorization, or a new Thread with a fresh Prompt Load Boundary. Continuation clearly identifies that retained conversation, disclosed material, recalled Memory, tool results, and represented attachments may be shared; it does not auto-redact the coherent history. Independent Dream, Reflection, and Sub-Agent contexts receive only their own bounded inputs rather than inheriting the complete ordinary Thread.

For staged Dream execution, a Provider Failure stops only the affected extraction scope. Successful Project and Unscoped results remain pending and reusable; the failed scope receives no automatic retry, fallback, or model switch. The User may retry it manually or explicitly skip it for the current Dream. Global Dream Synthesis may proceed with Partial Dream Coverage only after every failed scope has been retried successfully or explicitly skipped, and the resulting coverage limitation remains visible through proposal and patch review.
