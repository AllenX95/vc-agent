# Use Staged Context Isolation For Investment Reflection

Accepted: Investment Reflection uses a multi-agent-style two-stage flow with isolated model contexts in either Project or Unscoped scope. An Independent Evidence Pass analyzes evidence authorized by that Thread scope without personal memory and hands a bounded, evidence-referenced Independent Assessment to a separate Memory-Aware Reflection Pass; raw materials, the first-stage transcript, and full model reasoning are not copied forward. The second pass may retrieve bounded authorized excerpts through Evidence Drilldown when a cited claim needs verification, but it must not reload complete materials. This reduces context growth and memory anchoring while preserving auditability and Project isolation, at the cost of maintaining an explicit intermediate handoff and potentially performing additional model calls.

A Project Reflection may start from the broad objective `Review this Project`; the User does not need to define a narrower question or preselect materials. Broad launch gives the Independent Evidence Pass only a bounded, non-memory Reflection Project Brief and lets it choose evidence through Progressive Material Disclosure. It does not preload the whole Project, Project Memory, Long-term Memory, or prior investment conclusions.

An Unscoped Reflection starts from an ordinary Unscoped Thread but creates a separate dedicated Unscoped Reflection Thread. Its frozen brief contains only bounded explicit User inputs and direct-attachment cards from the source Thread. The Independent Evidence Pass may use that brief and public web capabilities, while the Memory-Aware pass may use Long-term Memory. Neither stage receives Project State, Project Memory, Project materials, or a Project association. The dedicated Thread inherits the source Thread's selected Output Location at creation; confirmation requires an Output Location and writes the Judgment Record there.

After the Independent Assessment exists, the Memory-Aware Reflection Pass may autonomously retrieve relevant active Project Memory and Long-term Memory through bounded card-then-expand recall. Relevance may be direct through Local Memory Provenance linking a learning to the current Project, or inferred from the Project brief and assessment, including industry, financing stage, applicability, risk, diligence questions, counterarguments, and uncertainty. Direct provenance may raise retrieval priority but does not make a memory correct or turn it into source evidence. Ordinary recall remains de-identified and visible, unresolved conflicts are recalled together, and `explicit-only` Long-term Memory still requires explicit User intent.

The Reflection run freezes a Workflow Prompt Snapshot at launch. Both stages and any explicit post-restart resume use that System Prompt Revision even if the active revision changes meanwhile, preventing one Judgment Record or Long-term Learning Proposal from being formed under mixed base instructions.

## L3 Execution Boundary

The implemented Project Independent Evidence Pass is a dedicated workflow run and Project Thread, not an ordinary conversational Turn. The Host persists its frozen brief, objective, framing, Prompt Snapshot, effective Profile, status, sanitized failure, session reference, and final structured assessment in `reflection_runs`. It does not register the workflow session as ordinary Physical Model Context or append the model's raw response to the user-facing Thread trajectory.

The stage starts only from `reflection.start.project` followed by the explicit `reflection.independent.start` action. A missing Profile leaves the run in `awaiting_profile`; failures and restart interruptions remain visible and require an explicit start with the same or a newly selected Profile. No fallback, automatic retry, or startup model call occurs.

The dedicated Worker receives an empty context history, the frozen Minimal VC System Prompt, Independent Evidence instructions, the bounded Reflection Project Brief, and only `material_recall`. The Host rejects every other capability request before execution. The final response must parse against the versioned Independent Assessment schema; arbitrary prose is a failed stage, not an accepted handoff. The Worker is retired at the stage boundary so the later Memory-Aware pass cannot inherit its physical context.

## L4 Memory-Aware Dialogue Boundary

The Memory-Aware stage starts only after a completed Independent Assessment and a second explicit User action. It freezes an independently selected `memory_aware_reflection` Task Model Profile on the run, starts a new physical context, and uses the run's original Workflow Prompt Snapshot. The initial Provider input contains only the objective, optional focus, bounded basic brief, Independent Assessment, and Critical Reflection instructions. It does not load the Independent Evidence session or first-stage transcript.

The model autonomously queries `project_memory` and `long_term_memory` through visible card-then-expand recall. The Host may apply a small same-Project Local Memory Provenance score boost internally, but neither the mapping nor the reason for that boost enters the Provider payload. Semantic query terms remain responsible for eligibility. Automatic recall still excludes `explicit-only` entries; an explicit User request changes recall mode only for that User turn.

Project Memory-Aware turns expose only `memory_recall`, `project_state_recall`, and `reflection_evidence_drilldown`; Unscoped turns expose only `memory_recall`. The dedicated drilldown accepts only a reference already present in the frozen Independent Assessment, parses an exact Material block and content hash, and caps each excerpt at 6,000 characters. It cannot browse Material cards, search by query, choose another block, or request full content. Changed, stale, malformed, missing, and empty references return no excerpt and explicitly require the handoff claim to be treated as unsupported until re-established. A resolved excerpt is not itself a support verdict; the model must compare the source text with the claim. Total recalled bodies remain capped at 32,000 bytes per turn and every call is a visible trajectory activity.

On restart, an unfinished initial Memory-Aware turn becomes interrupted and waits for explicit retry. A completed dialogue and its physical context are loaded without starting Pi. Subsequent dialogue turns retain the frozen Prompt Snapshot and Memory-Aware Profile; they do not inherit an ordinary Thread override.

## L4 Confirmed Outcome Boundary

Reflection outcomes use two distinct authority transitions. The model may call `reflection_outcome_propose` only on an active Reflection dialogue Turn where the User explicitly asks to prepare a Judgment Record or Long-term Learning Proposal. The call writes recoverable, non-authoritative drafts to an append-only local outcome log. It does not write a Project record, prepare a Memory patch, or change active Memory. Ordinary dialogue and unresolved or discarded Reflections therefore produce no durable investment conclusion by default.

The User confirms a Judgment Record separately. For Project Reflection, confirmation writes a paired Markdown and JSON record under `outputs/system/judgment-records/`, preserving the view, reasoning, uncertainty, counterarguments, evidence references, decision state, source availability, and an opaque local source reference. Learning Proposals remain drafts after that confirmation.

A Learning Proposal can enter Memory Evolution only when paired with a confirmed Judgment Record from the same Reflection run. The Host, rather than the model, adds the opaque source reference and Local Memory Provenance, then calls the shared L2 patch preparation path. Active Memory remains unchanged until the User reviews the lineage and five-file diff and confirms the patch. Discarding the preview returns the proposal to draft so it can be prepared again; committing it marks the proposal `adopted`. This status is the authoritative boundary for later Dream eligibility work.

The Host records dependency snapshots on proposed outcomes rather than trusting model-declared concurrency metadata. Snapshots cover exact stable Material versions, Memory entries actually recalled in the Reflection trajectory, and Learning Proposal target entries. Outcome listing, Judgment confirmation, and Memory patch preparation revalidate those dependencies locally without Pi or network access. Relevant changes append a recoverable `outcome.stale` transition, discard an uncommitted patch preview, and block authority transitions until the dialogue produces a replacement. Unrelated changes do not stale the outcome. Internal dependency hashes remain in app-local state and are excluded from confirmed Judgment Record files. Confirmed Judgment Records and adopted learning never transition to stale.

The current implementation completes this boundary for both Project and Unscoped Reflection, including scope-aware Local Memory Provenance, stable-reference Evidence Drilldown, and target-dependent outcome staleness. Direct attachments are represented by the Unscoped brief contract but are not populated until ordinary attachment plumbing exists. Dream eligibility filtering remains later L4/L5 work and is not implied by either completed path.
